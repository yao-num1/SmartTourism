1　应用背景与痛点

文旅消费长期存在三处结构性错配。游客侧：攻略、票价、开放时间、天气、路线分散在多个入口，一条行程要自己反复核对拼接， 而通用大模型给出的价格与营业时间常常已经过期，越具体越容易错。商户侧：中小景区、民宿与文创店主既不会写文案也请不起设计， 一条素材以小时计，做完就停在一段文字上，没有可落地的转化入口。运营侧：把 AI 接进真实业务时，最贵的不是模型调用费， 而是「错了没人知道」——幻觉无法拦截、成本无法核算、长对话无法收敛。

本项目针对这三处错配做成一套可直接部署的完整系统：以客群画像驱动的行程规划与营销素材生成作为两条主链路； 以数据来源分层 + 三道闸口守住真实性；以上下文预算与真实 token 计量守住成本； 并把产出物本身（带二维码的数字名片）做成获客入口，让「生成」与「转化」在同一条链路上闭合。

1.1 需求边界：做什么、不做什么

做：行程规划与动态调整、行程内消费触点、营销文案与文创数字名片、长对话稳定运行、运行成本与数据出处可核。 不做：不接支付与真实下单（只提供官方购票深链跳转到平台），不做需要个人身份的功能， 也不承诺转化率——未做人工对照实验，故不给「效率提升 N%」这类结论，人工耗时基线只作经验估计并标注。

1.2 三条设计约束：为什么不是「接一个大模型 API」

文旅场景里，「接个大模型」和「做成一个能用的系统」之间隔着三件事，本项目的架构选择全部围绕这三件事展开。 第一是真实性：通用模型给出的票价与开放时间常常已经过期，而且越具体越像真的。本系统不把这件事交给一句提示词， 而是把它做成系统属性——数据来源分四层按优先级接入、每层不可用都有明确退路、每张结果卡片都带出处徽标（见 3.4、3.5）。

第二是成本：对话越长历史越长，输入 token 线性膨胀，费用与延迟都不可预期。本系统给输入上硬预算 （CTX_BUDGET = 24000），把每轮都变的值排到提示词末尾以吃上游缓存命中， 并按真实 usage 逐场景计量而不是按公开单价推算（见 3.3、3.7）。

第三是可用性：产出必须落到一个可执行的对象上，而不是一段还要人再加工的文字。 行程要能落到可导航的路线与可点开的购票深链，素材要能落到可复制的正文与可印刷的二维码名片， 数据要能落到一键导出的整包文件——「印码即媒介」就是这个意思：产出物本身就是入口（见 2.3、4.1）。

2　场景描述与目标用户

2.1 三类目标用户

自由行游客要一条能直接出发的行程：几点到、怎么去、门票多少、下雨怎么改，而不是又一篇攻略
文旅商户景区、民宿、餐饮、文创店主：要能直接发的文案与带扫码入口的成品素材
运营与推广方需要按客群批量出内容、看真实热度、算得清每次调用花了多少

2.2 场景一　一次自由行，从想法到出发

① 说需求缺要素先被追问，不靠猜
→
② 选客群七类同行关系定节奏
→
③ 出行程含时段、路线、票价与深链
→
④ 接着改「第二天太赶」就地重排
→
⑤ 带走导出、分享、存为我的攻略

用户只说「出去玩三天」时，系统不补全假设，而是返回澄清问题，把目的地、天数、预算、人群补齐后才开始生成。 生成过程分阶段可见：思考 → 检索 → 规划 → 审校。产出里的地点带开放时间、票价、地址与来源标注， 实时数据可用时价格标「来源：美团（实时）」并挂购票直达链接，取不到时明写「暂未获取到实时数据」而不编数， 并给出体力节奏与雨天替代路线。行程可在同一会话里连续修改，不必重头再问。一次完整行程生成总耗时 50.03s、输出 1,444 字（含实时天气与票价采集，非纯模型耗时）实测。

2.3 场景二　一条素材，变成一张能扫码的名片

商户选一个景点或文创产品，一次成文：正文文案与平台适配版本一起出，广告法极限词等合规口径写进成文规格， 数字类内容只走卡片式呈现，文创产品则单独出「数字名片」形态。单篇文案生成 6.66s、首字 1.21s、成文 1,227 字实测。 文案可一键转成带二维码的数字名片，印刷到包装、桌牌或展板上，扫码即达这条内容页—— 把转化路径从「回去搜一下」缩短成「当场扫一下」，这是本项目「印码即媒介」的落点。

2.4 七类同行关系与差异化产出

规划界面上的「同行关系」有七个选项：情侣/伴侣、亲子家庭、朋友/闺蜜、银发同行、商务差旅、团建团队、独自旅行， 归一化后落到七套成文客群策略（详见 4.2）。换不同客群即产出可复现的差异化方案——每日景点数、动线密度、 住宿品类、餐饮档次与消费点清单都会变，不是同一模板换措辞。这一条通过多次调用 /api/plan 对比验证实测。

2.5 客群差异不是换措辞：策略库里的原文

差异化不靠提示词里加一句「请考虑老年人」，而是有两处可查的口径。tourism-advisor 的 CROWD_STRATEGIES 为规划侧七类客群各给出景点、住宿、餐饮、节奏与消费点五项策略， 直接决定动线密度与住宿品类；smart-matching 另有六类客群画像库 （/api/health 实测返回 crowds_loaded: 6），服务匹配与营销侧。 两段原文可以直接对比：银发康养的节奏是「慢节奏，每天 1-2 个景点，步行为主」，住宿要求「电梯、低楼层、安静、医疗配套、无障碍」， 餐饮是「清淡、软食、养生餐、正餐准时」；学生穷游的节奏是「紧凑高效，公共交通，每天 3-4 个景点」， 住宿是「青旅、民宿床位、交通便利、安全」，餐饮是「本地小吃、性价比优先、分量大」。 同一座城市换到这两类客群下，规则骨架层就落到不同的每日景点数与不同的住宿品类上——差异发生在行程结构上，而不是文案措辞上。

消费触点同样在策略库里成表：亲子家庭挂「亲子套票 / 儿童体验项目 / 主题餐厅」，情侣挂「情侣套餐 / 夜游演艺 / 摄影服务」， 银发康养挂「康养体验 / 文化讲解 / 适老化文创」。行程因此天然带着「到哪里可以花钱」的入口，而不只是一张观光清单， 这是把规划与转化放进同一条链路的做法。

2.6 场景三　一条长对话里的可控性

规划与营销之外，第三个场景是「用得久」。真实用户不会一问一答就走，而多数演示在第三轮就开始丢前面的约束。 本系统把对话控制做成四项能力：多会话并行（会话列表按用户隔离，新建对话不再删除历史）、 停止生成（真停上游流并释放线程，半截答复按「可能不完整」落库，不冒充完整答复）、 重新生成 / 编辑重发（撤回只撤「这一轮」，比对不上就一律不删，防误删历史）、 点赞点踩（反馈落库，回放时投票状态不丢，规则指标进运维面板）。

这四条按主题分文件写成回归：test_session_management 76 项、 test_stream_stop 71 项、test_regenerate 44 项、 test_feedback_metrics 112 项，合计 303 项实测。 另有上下文占用进度条与到 75% 触发线自动压缩（test_context_manager 57 项）， 让「聊得长」在界面上是看得见的状态，而不是等回答变慢才发现。

76 项多会话：列表按用户隔离，新建对话不删历史
71 项停止生成：上游流真停、线程释放、半截标「可能不完整」
44 项重新生成 / 编辑重发：只撤这一轮，比对不上不删
112 项点赞点踩：反馈落库，回放时投票状态不丢

这四条看着不像「AI 亮点」，但没有它们，长对话产品的证据就积累不起来：反馈不落库就没有答复质量指标， 停止不真停就说不清上游流占了多少线程，会话不隔离就没法把成本按场景归账，摘要不落库就会在重启后丢掉已确认的预算与人群。 本项目把这四件事都做成有断言的功能，而不是留给运气，也不写进「后续规划」。

3　技术创新点

3.3 长对话上下文：把 token 从「线性膨胀」变成「预算内恒定」

旧做法固定取最近 20 条历史，长对话必然带来上下文膨胀、早期硬约束丢失与漂移。本系统给输入 token 上硬预算： CTX_BUDGET = 24000，最近 4 轮无条件必保（宁可超预算也不断裂），更旧轮次贪心装入， 装不下则折叠进滚动摘要（压成 ≤150 字，硬上限 300 字）；摘要与已确认事实（目的地 / 天数 / 预算 / 人群）落库， 服务重启不会「首轮失忆」。占用到 75% 自动压缩并显示进度条。零第三方依赖：不引入分词器与向量库， CJK 每字≈1、其余 len/4 保守近似，宁可高估不超发。

3.5 三道闸口 + 「降级不静默」

  • 第一道 · 输入闸口：必填三要素缺失即返回澄清话术，先于任何生成发生。
  • 第二道 · 数据闸口：价格 / 图片 / 开放时间只认实时接口与库内真实数据，缺失走占位与「暂未核实」。
  • 第三道 · 输出闸口：模型输出经 validation 校验（绝对化用语、无来源价格、编造图片链接）， 问题以 SSE 事件如实下发给前端，而不是悄悄改掉。

校验环节本身也可能出错，因此它按环节兜住，把 runs / issues / degraded_runs / by_stage / last_error 聚合进面板——能看到「哪一环掉过几次」，而不是把一次降级吞成正常通过。回归 test_validation_degrade.py 42 项实测。

3.6 检索出处可见：没有命中就不出标注

本地知识库走 BM25 + 向量的混合检索。每轮答复若命中库内片段，后端下发 sources 事件、 前端渲染「参考来源」卡片，标题与出处可点验；没有命中就不出标注，不做「看起来有出处」的假标注。 回归 test_rag_sources.py 38 项实测。 如实说明：混合检索已在请求路径接线，当前面板状态为 wired_idle（不称「已命中」）。

3.8 模型层：运行期热切换 + 两级容错

国产大模型的可用性会变（限流、调价、欠费、接口调整），因此模型不写成编译期依赖： DeepSeek / 智谱 / 通义 / Kimi 经 /api/config 与 /api/providers 运行期热切换， 默认 deepseek-chat，配置目录不进提交包。发送层另加退避重试 （1 次、1.5s 退避，只对 timeout / network / busy / server 四类可重试错误生效）与备用通道 （SMARTTOURISM_LLM_FALLBACK_BASE_URL / _KEY / _MODEL）——主通道故障时改道，而不是把错误直接抛给用户。 非流式 120s、流式 180s，流式另有看门狗，超时按中断处理并保留已生成部分。

数据侧与生图侧同样按「会失败」设计：美团接口 timeout 30s、结果缓存 TTL 300s、stale 上限 24h（实测上游 11–44s）， 故障时回退最近一次成功数据并在提示词里标明「这是多久前的数据、仅供参考」，绝不拿旧价假装实时价； 高德按锁 + 最小间隔 0.16s + 3 次尝试封装限流；生图统一走火山方舟 Seedream，带参数自适应重试与 「场景 Key 欠费回落共享 Key」两级容错，并把生图 150s / 拉图 60s / 前端 abort 215s 对齐， 修掉「上游已计费、本地先放弃」的错位。这一层的回归为 test_llm_retry 57 项、 test_dao_guard 40 项、test_hotpath_degrade 39 项、 test_concurrency 22 项实测。

5　已知边界与复现方式

5.1 已知限制

  • 首字延迟偏高：行程场景首字 40.99s，因前置采集（定位 / 实时数据 / 检索）在生成之前。 是否改为流式优先属产品决策，当前未实现，不粉饰为已优化。
  • 生图依赖上游账户额度：欠费时出图直接失败，系统回退占位图并写明原因、可重试，不假称成功。
  • 混合检索当前为空闲状态：已在请求路径接线，但面板实例未触发索引构建，故标注为空闲而非已命中。
  • 成本样本量有限：实测成本来自 4 个场景 7 次调用的单次进程累计，代表「这一遍跑出来的量」，不是大样本统计。
  • 无交易闭环：只提供官方购票深链，不代下单、不接支付，无法声称闭环成交能力。
  • 多人偏好平衡靠规则承接：同行人群含多种偏好时，由提示词规则与固定输出模块处理，未实现独立的偏好求解算法。
  • 校验层只证来源、不证对错：validation 覆盖绝对化用语、无来源价格与编造图片链接， 词表与正则的覆盖始终有限，故其通过率只当过程计数，不当质量结论。
  • 单文件体量偏大：app.py 7,684 行、前端单页 10,440 行，可读性与可维护性是明确技术债，列为后续拆分项。

5.2 数据口径约定

全文数字分三类并逐条标注：实测——由脚本或面板读自真实运行系统，附复现命令； 估算——口径公开可复核；预期——尚未验证的目标或经验基线， 尤其是人工耗时对照，只作假设不作结论。三类不混用、不互相冒充。

实测读自运行中的系统：回归项数、面板计数、逐场景 token 与延迟，均可一条命令复现

预期尚未验证的目标与经验基线，如人工耗时对照，写在限制里而不是亮点里
